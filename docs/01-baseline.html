Chapter 1

The starting point: a 13.5 GB specialist that scores 74/100

The subject of this pipeline is the finetuned medical checkpoint from the sibling walkthrough: BioMistral-7B with its medical LoRA adapter merged in — one dense model of 7.24 billion weights, about 13.5 GB at fp16 (16-bit floating point, 2 bytes per weight). Compression asks a blunt question: how much of that can we throw away before the behavior we paid for goes with it?

Where this model sits in the lifecycle

A model like this passes through stages, each in its own repo in this series. Pretraining gave it medical knowledge; finetuning (the sibling walkthrough) gave it its Q&A behavior; an alignment stage (DPO/GRPO, in medical-llm-RL) later tuned its preferences — and, notably, left held-out test accuracy unchanged. That is why compressing the SFT checkpoint is fair game: compression preserves what its input model does, and the aligned model does the same thing on this test.

The exam every claim is graded on

Compression without measurement is just deletion. Before touching a single weight, the run froze an evaluation harness and used it after every step: the same 100 held-out PubMedQA questions the model never trained on, the same prompt, greedy decoding (always pick the most likely token — no sampling randomness), and a strict grading rule: the first word of the answer must be yes, no, or maybe and match the reference.

# the exact prompt, from all four run scripts
You are a medical QA assistant. Answer with yes, no, or maybe first,
then a brief rationale.

Instruction: {the question}
Context: {the study abstract}
Answer: yes …   ← only this first word is graded
Calibrate your eyes before reading any chart in this series: one question is one point. On a 100-question exam at this accuracy level, re-rolling the dice moves the score by ±4 points quite naturally (one standard error). So a 2-point wiggle between two checkpoints means nothing, while the 13-point pruning drop and 18-point distillation rebound you're about to see are real signal.

Why compress at all: the VRAM wall

At fp16, just holding this model's weights takes ~13.5 GB of GPU memory — before counting activations and the KV cache that inference adds on top. That single number decides which hardware can run the model at all. Every byte removed also has to travel from memory to compute on every token generated, so smaller models aren't just cheaper to fit — they're faster to read.

The plan: three moves, in a deliberate order

Each technique removes a different kind of fat, and each has a chapter:

  1. Prune (Chapter 2) — delete the individual weights that contribute least, using a score computed from real medical prompts. Removes parameters.
  2. Distill (Chapter 3) — let the original, uncompressed model teach its pruned self to close the quality gap. Restores behavior.
  3. Quantize (Chapter 4) — store every surviving weight in fewer bits. Removes bytes per parameter.

The success criteria were set before the experiments, not after: accuracy drop within 1–2% of baseline (which on this 100-question exam means 1–2 points), no new unsafe behavior, and a real VRAM reduction. Chapter 5 grades the pipeline against them.
