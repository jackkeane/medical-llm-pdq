Chapter 6

Serving: the compressed model behind a real API

Five chapters produced a 3.8 GB checkpoint that scores 80/100. This one puts it to work: loaded into vLLM, an inference server, on the same RTX 4090, answering over HTTP. The payoff shows up here in two measured numbers — the weights load in 3.6 seconds, and because they take only 3.88 GiB, the rest of the card holds 2.24× more conversation than the uncompressed model could. Compression didn't just make the model fit; it made it serve.

From checkpoint to endpoint

A checkpoint on disk isn't a service. Something has to hold the weights in GPU memory, accept requests, batch them, run the forward passes, and stream tokens back. That's an inference server; here it's vLLM, which speaks the OpenAI API so any client that talks to OpenAI talks to this model unchanged. The whole launch is one command:

# serve_vllm.sh — the deployable artifact behind an HTTP endpoint
vllm serve artifacts/awq-w4a16-stage3 \
    --served-model-name medical-7b-compressed \
    --port 8801 --max-model-len 4096

Note which artifact ships. Chapter 4 kept NF4 as the default for a single-process load, and reached for AWQ W4A16 only "when a serving stack specifically requires that format." vLLM is exactly that stack — AWQ W4A16 is its native 4-bit path — so the server loads the AWQ export. It scores 80/100, statistically identical to NF4's 81 (Chapter 1's ±4-point noise), and now it's in the format the serving engine wants.

The exam still passes — over HTTP this time

Every previous chapter graded the model in-process. Here the same 100 held-out questions go out as API calls, greedy decoding (so the answer is deterministic), first word graded. The endpoint returns 80/100 — the identical score the AWQ export earned offline in Chapter 4. Same weights, same answers, now across a socket:

80 here, 81 in Chapter 4 — same model, not a regression. Chapter 4's 81 was the NF4 build; this is the AWQ build vLLM serves, which scored 80 both offline and over the API. One question out of a hundred is inside the exam's ±4-point noise. The point of re-running it through the server isn't a new number — it's proof the number survives deployment.

Memory at serve time: the weights are the small part

Chapter 1 warned that weights are "only part of the bill — activations and KV cache come on top." Serving is where that bill comes due. Every active conversation needs a slice of KV cache (the per-token attention state), and that cache shares the card with the weights. Shrinking the weights hands the freed space straight to the cache. Loaded side by side on the same 24 GiB card, same 4096-token context limit:

This is the serving-time dividend of compression. Fitting a smaller model on a given GPU is the obvious win. The subtler, bigger one: the 9.6 GiB the AWQ weights don't occupy becomes KV cache, so the same card serves 2.24× the concurrent users — or one user with 2.24× the context. Compression buys throughput and context length, not merely a checkbox that says "it fits."

Throughput: batching is the multiplier

A single request decodes at about 150 tokens/second. That feels slow because generating one token reads the entire model from GPU memory to produce a single number — the GPU is starved for work, not compute. Serve many requests at once and they share each weight read (vLLM's continuous batching), so aggregate throughput climbs steeply while any one user still sees snappy replies:

Where the curve stops: an honest note. Pushed to 64 simultaneous requests on this machine, throughput collapsed to ~380 tok/s and every request took ~21 s instead of under a second. It wasn't a full KV cache (usage stayed under 6%) or a request queue (none formed) — the server log shows 64 running, none waiting. The slowdown is specific to this WSL2 box, where vLLM itself warns it runs with pinned memory disabled; a bare-metal Linux server would be expected to scale further. Treat this as an environment artifact, not a property of the model, so the chart stops at the last clean point (48). Reporting the cliff rather than hiding it is the same rule the whole series follows.

What ships, and the honest limits

Two supported ways to run the final model, matched to the job:

  • Throughput server → AWQ W4A16 via vLLM (this chapter): one command, OpenAI-compatible, continuous batching, 80/100. Use it to serve many users.
  • Single-process app → NF4 via bitsandbytes (Chapter 5's snippet): a plain from_pretrained load, 81/100, no server to run. Use it for a script, a notebook, or one embedded worker.

Both are the same distilled stage-3 checkpoint from Chapter 3, differing only in the 4-bit format each stack prefers — and scoring within one point of each other.

What this chapter did not prove. One GPU, one machine — no replication, autoscaling, or failover. The throughput numbers are from a WSL2 box and should be treated as a lower bound. And the exam still measures only yes/no/maybe accuracy: the safety and hallucination evaluation Chapter 5 flagged as missing is still missing, and it matters more, not less, once the model is reachable over a network. This is a working deployment, not a production-hardened one.

Where these numbers come from

Every figure on this page was produced by, and can be reproduced with, two files added to the repo for this chapter:

  • serve_vllm.sh — the one-line launcher shown above
  • run_vllm_serving_benchmark.py — drives the endpoint: the 100-question exam, the concurrency sweep, and the memory readout
  • reports/vllm_serving_metrics.json / .md — the machine-readable results, including the fp16-vs-AWQ footprint table

Load-time facts (3.88 GiB / 3.6 s, 17.36 GiB and 142,208-token KV cache; 13.5 GiB / 7.75 GiB / 63,456 tokens for the fp16 comparison) are read directly from vLLM's own startup log on the RTX 4090.
